# 기능 작업 흐름과 공통 계약 경계

[English](architecture.md) | [한국어](architecture.ko.md)

## 새 기능 작업 흐름

| 단계 | 담당 | 다음 단계에 전달할 산출물 |
| --- | --- | --- |
| 1. 기획 | `planning` | `docs/plans/`의 승인된 제품 범위·흐름·상태·완료 조건 |
| 2. Figma 디자인 | `design` | Figma MCP 도구로 Figma에 직접 그린 검토된 디자인과 파일·노드 참조, 플랫폼 차이. 승인된 시각 방향이 없으면 그리기 전에 ui-ux-pro-max 방향 시드를 선택적으로 실행한다 |
| 3. 디자인 시스템 생성 | `design` | 승인된 Figma 파일에서 도출한 승인된 Figma 컴포넌트·Variant·의미 기반 토큰 |
| 4. 디자인 토큰 매칭 | `design` | Figma와 네이티브의 토큰·컴포넌트 대응, `app/design/design-system-map.yaml`의 실제 예외, 인계 문서의 신규 심볼 계획 |
| 5. 네이티브 앱 개발 | `app` | 로컬 fixture·테스트 대역으로 동작하는 Compose·SwiftUI 흐름, 플랫폼·화면 검증 증거, 확인된 데이터 요구 |
| 6. GraphQL 계약 생성 | `app` 작성, `backend` 검토 | 구현된 앱 흐름에서 도출한 입력·출력·nullability·실패 의미를 담은 합의된 루트 SDL |
| 7. 백엔드 개발 | `backend` | 합의한 계약에 따른 서버 구현·백엔드 검사, endpoint와 소비 코드 인계 |

토큰 매칭은 GraphQL을 기다리지 않는다. 실제 승인된 Figma 파일을 확인한 뒤 디자인 시스템을 도출하며 방향 시드나 승인되지 않은 초안에 승인된 컴포넌트 라이브러리나 네이티브 앱 구현이 이미 있다고 주장하지 않는다. 기존 승인은 재사용하고 미결정 디자인·데이터 사항은 담당 영역의 인계에 기록한다.

계약이 없어도 앱 단계에서 네이티브 화면·Navigation·상태·로컬 동작과 흐름 검증에 필요한 앱 소유 모델·테스트 대역을 구현한다. 임시 fixture는 UX 예시이며 서버 응답 보장이 아니다. 계약 인계 과정에서 앱 모델·Operation·fixture를 확정된 SDL에 맞추고 GraphQL 연동 전에 Apollo를 재생성한다. 백엔드 완성 뒤 요청된 앱 연결·통합 검사를 마무리한다. 앞선 앱 단계만으로 실제 통합이 증명되지는 않는다. 완전히 로컬인 기능에는 억지로 GraphQL 계약이나 백엔드 작업을 추가하지 않는다.

새 기능에 이 순서를 적용하며 기존 기능이나 한정된 수정에서 처음부터 다시 시작하도록 강제하지 않는다. 현재 계약으로 충분하면 재사용한다. 인계만으로 다음 영역을 자동 시작할 권한이 생기지는 않으며 사용자 요청 범위를 따른다. 구현 상세는 각 영역에 둔다: [백엔드](../backend/docs/architecture.ko.md) 또는 [앱](../app/docs/architecture.ko.md). 해당 영역만 읽는다.

## 공통 계약 소유권

백엔드와 앱은 독립된 개발 영역이다. 공통 API 합의는 동작 설명을 포함한 `contracts/graphql/`의 단일 SDL 원본이다. 앱 흐름 검증 뒤 앱 영역이 필요한 SDL draft를 소유하고, backend 영역이 구현 가능성을 검토해 서버 구현 전에 app과 계약을 확정한다. GraphQL 우선은 서버에서 계약을 구현보다 먼저 정한다는 뜻이며 제품 디자인·앱 시제품 제작의 순서를 뜻하지 않는다.

## 계약 변경과 인계

1. 현재 계약으로 요구를 충족하면 재사용한다. 상대 구현을 읽어서 API 동작을 알아내지 않는다.
2. 입력·필드·nullability·실패 동작이 부족하면 임시임을 명시한 로컬 fixture로 앱 흐름을 먼저 검증한 뒤 필요한 SDL 변경 draft를 작성한다. backend 영역은 앱 소스 대신 계약 인계로 구현 가능성을 검토한다. GraphQL 연동과 의존하는 백엔드 구현 전에 계약을 확정하고 타입으로 표현할 수 없는 의미는 SDL 설명을 사용한다. 계약 검토로 제품·UX 결정이 바뀌면 기획·디자인으로 되돌리며 fixture만으로 서버 동작이 정해지지는 않는다.
3. 가능한 호환성을 유지한다. 호환성을 깨는 제안에는 전환·배포 순서를 명시한다. Schema 수정만으로 소비 코드 호환성이 증명되지는 않는다. 한 영역 작업의 일부로 상대 구현을 다시 작성하지 않는다.
4. 현재 영역만 재생성·검사한다. 계약 diff, 예상 요청·응답·오류 동작, 자체 검증 증거, 남은 상대 영역·통합 검사를 인계한다. 받는 영역은 보낸 영역의 코드가 아니라 계약을 사용한다.
5. 영역 간 조사·구현·end-to-end 검증은 명시적 통합 작업이 필요하다. Mock과 개별 테스트는 배포된 양쪽이 함께 동작한다는 증거가 아니다.

계약 결정에는 [공통 기능 기록](features/_template.ko.md)을 사용하고 구현 메모는 소유 영역의 `docs/features/`에 둔다. 기존 [system 기록](features/system.ko.md)은 영역 간 통합 참고 자료이며 일반 백엔드·앱 개발의 필수 읽기 자료가 아니다.

## 공통 한계

참고 문서는 선택지이며 의존성 설치 목록이 아니다. 실제 구현 요구에 필요한 인프라만 추가하고 예시 제품 도메인은 넣지 않는다. 구조 검사기는 일부 경계를 감지할 뿐 전체 아키텍처나 접근 통제를 강제하지 않는다. 읽기 규칙이 파일 시스템 sandbox를 만드는 것은 아니다.
