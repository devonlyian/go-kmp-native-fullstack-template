# Product internationalization (i18n)

[English](i18n.md) | [한국어](i18n.ko.md)

This is the product-language policy for features built with this template. Markdown translation is handled separately by `sync-docs`. Read the product defaults and your role's section; this policy does not expand role boundaries. An explicitly approved product requirement can override a default; record the exception in the feature plan and carry it through the handoff.

## Product defaults

- Ship Korean (`ko`) and English (`en`) in the same app with the same functionality. New and changed user-facing flows must cover both languages; when updating an existing product, record unrelated localization gaps separately.
- Follow the platform's language resolution, including an OS per-app language choice where supported. Match supported languages from the user's ordered preferences; use English when none match. Use language tags, not country, SIM, or time zone, to select language. Do not add an in-app language picker unless requested in the feature scope.
- Cover app-owned labels, navigation, dialogs, validation/error/retry/empty-state copy, accessibility labels/hints, and permission explanations. Preserve approved brand names and user-authored content; identify intentional untranslated text. System-owned prompts follow the OS.
- Translation must preserve meaning, actions, tone, and placeholders. Fallback protects unsupported locales; it is not acceptance evidence for missing Korean or English translations. Format dates, numbers, quantities, and money using platform locale facilities; language alone must not change stored values, time zone, or currency.

## Planning

Record supported languages, fallback and language-selection behavior, content exceptions, and observable acceptance for both languages in the existing feature plan. Inherit the defaults instead of asking again for every feature. Identify any localized remote content or locale-sensitive business rules for a later contract handoff; do not choose resources, APIs, or storage from planning.

## Design

Provide Korean and English copy for each planned state, including accessibility content, in the existing design record or referenced design. Show both versions of the proof screen in the same Figma file/page. Reuse existing approval; for a scoped fix, review the affected states without restarting the full design flow. Use paired variants of text-sensitive screens to check Hangul glyphs, line height, wrapping, long English labels, small screens, and larger text sizes. Shared layout/components remain shared; do not create separate product files or Design Systems just for language.

Hand off the actual copy source, translation review state, approved exceptions, and per-language visual evidence. Distinguish draft translation from reviewed copy. Figma approval does not establish runtime locale selection or resource coverage.

## App development

Keep localization in native presentation, consistent with KMP's Domain/Data/Network boundary. Reuse the project's native localization mechanism; for a new template-based app use the following defaults. These are implementation instructions, not a claim that these files already exist.

| Platform | Resource and usage policy |
| --- | --- |
| Android / Compose | Keep complete English defaults in `res/values/strings.xml` and Korean in `res/values-ko/strings.xml`; use native string/plural resources from Compose. Configure supported locales for OS per-app language selection and ensure both translations are packaged. |
| iOS / SwiftUI | Use a String Catalog (`Localizable.xcstrings`) with English source/development language and Korean translations. Reuse existing `.strings`/`.stringsdict` where appropriate rather than migrating unrelated resources. Verify target membership, supported localizations, development language, and localized app-owned permission text. |

Give each message a stable, contextual resource identity and translator context where needed. Reuse equivalent messages, not unrelated messages that happen to have the same English spelling. Bind user-facing text to native localization resources/APIs, including interpolated and accessibility text. SwiftUI literals passed to localizing APIs are allowed when extraction and both translations are verified; raw display strings or dynamic strings that bypass localization are not.

Use complete messages with typed placeholders and platform plural rules; do not build sentences by concatenating translated fragments or force the same plural categories in both languages. Keep types and argument identity consistent between translations. Do not put translated UI sentences or a custom translation engine in Shared. Map typed failures to localized messages in native UI, including a safe localized fallback for unknown failures; never show raw server/debug error text to users.

## Contract and backend handoff

UI-only translation needs no GraphQL or backend change. Keep protocol identifiers, enum values, error codes, and stored machine values stable across languages. For server-provided localized content, agree language negotiation, supported languages, fallback, and response/error semantics in the requested contract step before dependent implementation. Record server-generated user-facing messages and notifications as a separate backend localization responsibility when they are in scope. Do not infer a server locale from app fixtures or translate arbitrary server text at runtime. Each role uses the agreed contract and stays within its implementation scope.

## Verification and completion

For affected UI/resources, the app role records these checks in its feature record; design reviews the supplied renders. Use existing platform checks and relevant tests within the requested scope.

1. Check complete, reviewed `ko`/`en` coverage for affected messages, including placeholders, plurals, accessibility, permission text, and intentional exceptions. Missing translations, empty values, raw keys, or unreviewed fallback are not complete. Verify native resource extraction and packaging, not only the presence of files.
2. Exercise the affected flow on each target platform in both languages. Check success and relevant empty/error/retry states, interpolation and plural quantities, local formatting, text scaling, wrapping, and VoiceOver/TalkBack. Record evidence by platform and language; mark unavailable runs as unverified.
3. Check language resolution and changes: Korean and English preferences, an unsupported-only preference falling back to English, and an unsupported preference followed by a supported one. Verify OS per-app selection where supported and the resulting screen after the platform-required refresh/relaunch; test persistence only when an in-app selector is actually in scope.
4. Run affected platform builds/tests and inspect native localization diagnostics. Existing `./tools/verify.sh app` and `./tools/verify.sh ios` do not by themselves prove bilingual UI behavior. `./tools/verify.sh structure` checks repository/document structure, not app translations or rendering. Report completed checks and remaining platform/language gaps separately.

Native reference: [Android localization](https://developer.android.com/guide/topics/resources/localization), [Android per-app languages](https://developer.android.com/guide/topics/resources/app-languages), [Apple String Catalogs](https://developer.apple.com/documentation/xcode/localizing-and-varying-text-with-a-string-catalog), and [Apple localization testing](https://developer.apple.com/documentation/xcode/testing-localizations-when-running-your-app).
