# 기능 기획

[English](SKILL.md) | [한국어](SKILL.ko.md)

[기획 양식](../../../docs/plans/_template.ko.md)을 사용한다. 영어가 기준본이며 모든 기획 문서 수정에 [sync-docs](../sync-docs/SKILL.ko.md)를 사용한다. 기능마다 `docs/plans/`에 문서 쌍 하나만 두고 같은 제품 결정을 PRD·흐름·완료 조건 문서로 나누지 않는다.

1. 대상 사용자·문제·기대 결과·근거·요청된 승인 상태를 확인한다. 사용자가 제공한 사실과 가정을 구분한다. Figma·GraphQL·데이터베이스·백엔드·앱 구현에서 제품 의도를 추론하지 않는다.
2. 포함·제외 범위, 대상 플랫폼, 제품 제약, 미결정 사항에 대한 의존성을 정한다. UI 컴포넌트·API 필드·저장 방식·라이브러리·아키텍처를 선택하지 않고 사용자에게 보이는 의도를 설명한다.
3. 처음부터 끝까지의 흐름과 적용할 비즈니스 규칙을 정의한다. 성공과 실제 관련된 빈 상태·검증·권한·실패·재시도/복구·오프라인·취소 상태만 다룬다. 네이티브 상호작용 선택은 디자인에 맡긴다.
4. 관찰 가능한 완료 조건과 관련 접근성·개인정보 보호·안전 요구를 작성한다. 합의한 결정·가정·열린 질문을 기록한다. 사용자가 명시적으로 승인할 때까지 상태를 `Draft`로 유지하며 문서 생성이나 침묵을 승인으로 해석하지 않는다.
5. 범위를 바꾸는 중요한 선택은 확정 전에 짧은 질문 하나로 결정받는다. 그 외 작은 불확실성은 문서에 드러낸다. 승인 뒤 디자인 역할에는 흐름·상태·콘텐츠·플랫폼 제약을, 계약 draft 작성자인 app 범위에는 SDL 필드를 제안하지 않고 동작·데이터 개념·결과·실패 의미를 인계한다.

기획은 Figma, `contracts/graphql/`, 데이터베이스 파일, 프로덕션 코드, 구현 기록을 수정하지 않는다. 제공된 제품 문서만으로 실현 가능성이나 현재 동작을 확인할 수 없으면 구현 영역을 넘지 말고 담당 역할이 확인할 빈 부분으로 기록한다.
