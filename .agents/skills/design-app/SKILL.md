# Design the app

[English](SKILL.md) | [한국어](SKILL.ko.md)

Use [design rules](../../../app/design/AGENTS.md). Read English except for translation maintenance. Keep design records in `app/design/`; do not read backend implementation or edit app code or GraphQL.

Enter at the requested stage and reuse approved artifacts. Existing approved Figma designs or agreed local specifications do not need to be recreated; report missing source evidence only when it is needed for the requested change. Record every design task in a paired file under `app/design/history/` using [the design record template](../../../app/design/history/_template.md), named `YYYY-MM-DD-<feature-slug>.md` / `.ko.md`; keep its status current as the work moves.

Figma file convention: unless the user says otherwise, keep one Figma file per product and add one page per feature flow; record the file URL/key, page name, and node ids in the design record.

1. Confirm the approved feature plan before designing: user value, flow, target platforms, requested screens, content, and UI data concepts. Separate draft proposals from already-approved Figma or agreed local specifications. Do not read GraphQL or backend implementation as design input. Record ambiguous product decisions as planning gaps instead of letting an existing API pre-constrain the design.
2. Seed the visual direction when none is approved. Skip this step when an approved Figma design, an agreed local specification, or an established product visual identity already fixes the direction. Otherwise run `python3 .agents/skills/ui-ux-pro-max/scripts/search.py "<product and mood keywords>" --design-system` and present the returned style, semantic color tokens, typography pairing, and checklist as a direction candidate for user review. Filter the output for a native app before proposing it: landing-page patterns, hover/scroll effects, and web-only guidance do not apply; Google Fonts may serve as display faces while Android/iOS system fonts carry the UI. The seed is a recommendation, never an approved design; record the approved or rejected direction in the design record, and fall back to a written direction proposal when the script is unavailable.
3. Before drawing, verify Figma MCP access with a read-only call on the target file. If Figma MCP is unreachable or rate-limited, stop the task and report the failure; do not produce a substitute local specification or invent a file unless the user explicitly asks for one.
4. Draw one proof screen in Figma through the Figma MCP tools and get it approved before drawing the rest. Pick the most representative screen; approval of the proof screen approves the direction grammar (palette, type, component character, spacing), not the full flow. Before any Figma tool call, inspect available capabilities and load only the operation's available prerequisite skill: `figma-create-new-file` for new files, `figma-use` for file-context reads/writes, `figma-generate-design` for layouts, `figma-generate-library` for components/tokens, and `figma-design-to-code` before design-context retrieval. Use `figma-swiftui` when translating SwiftUI. Follow each skill's prerequisites. Figma writes require authorization in the task, not repeated confirmation for already-authorized work. Paid Code Connect is optional and used only when requested and available.
5. Produce the full design in the same Figma file/page, applying the approved proof-screen grammar. Reuse existing foundations and approved Figma components/variants, Variables, and Auto Layout when evidenced. Preserve native navigation, sheets, pickers, and safe areas for Android/Material and iOS/HIG instead of forcing identical interactions. Include relevant loading, empty, error, retry, disabled, and offline states. Obtain review of new design decisions before continuing; reuse an existing approval when it covers the work. Never invent a Figma file, node, or artifact.
6. Before requesting design approval, self-check the canvas: every planned state exists as a frame; platform frame sizes and safe areas are respected; native navigation metaphors are preserved; colors and text bind to semantic Variables rather than raw values; the design record lists the actual screens and node ids. Fix gaps before asking for review.
7. After design approval, create or reconcile the Design System from the approved Figma file or an agreed local specification. Keep the actual source and approval state explicit; a local specification does not establish that Figma nodes exist. Inspect existing foundations and targeted native components/screens, then define semantic color, typography, spacing, and radius tokens and finalize shared `Component`, `Token`, and `Layout` names where evidence supports them. Keep feature-specific components local; shared components belong in the Design System only when actual reuse warrants it. Do not invent existing native symbols for a planned implementation. Hand planned code additions to the app role.
8. Before native app development, match approved Design System tokens to verified existing Android/iOS names. Update `design-system-map.yaml` only for finalized mappings and actual naming or behavior exceptions; do not put GraphQL fields or planned native symbols in the map. Put planned native additions in the handoff, clearly labeled as planned rather than existing. The design role neither reads nor edits GraphQL.
9. Hand the approved design to the app scope for native app development with the design record path, Figma file/design reference, approval state, Design System evidence, existing token/component mappings and exceptions, planned native additions, platform differences, interaction states, accessibility requirements, and acceptance criteria. The app scope creates the GraphQL contract after native development and hands its approved contract to backend. If contract work requires a product or UX change, return it to planning/design review and obtain approval instead of silently changing the design. For visual review compare actual Android/iOS renders with the approved reference: spacing, type/line height, wrapping, color, radius, safe areas, dark mode, text scaling, and accessibility. Report differences and evidence separately for each platform. Request missing renders from app work; do not start backend work or claim that mocks, mappings, or an unrendered design prove visual parity.
