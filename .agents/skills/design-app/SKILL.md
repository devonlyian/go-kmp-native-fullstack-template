# Design the app

[English](SKILL.md) | [한국어](SKILL.ko.md)

Use [design rules](../../../app/design/AGENTS.md). Read English except for translation maintenance. Keep design records in `app/design/`; do not read backend implementation or edit app code or GraphQL.

1. Confirm the approved feature plan before designing: user value, flow, target platforms, requested screens, content, and UI data concepts. Separate draft proposals from already-approved Figma or agreed local specifications. Do not read GraphQL or backend implementation as design input. Record ambiguous product decisions as planning gaps instead of letting an existing API pre-constrain the design.
2. Produce, review, and approve the requested design draft. Reuse existing foundations and Figma components/variants, Variables, and Auto Layout when available, but do not update `design-system-map.yaml` yet. Preserve native navigation, sheets, pickers, and safe areas for Android/Material and iOS/HIG instead of forcing identical interactions. Include relevant loading, empty, error, retry, disabled, and offline states. Obtain review of new design decisions before continuing; reuse an existing approval when it covers the work. Before any Figma tool call, inspect available capabilities and load only the operation's available prerequisite skill: `figma-create-new-file` for new files, `figma-use` for file-context reads/writes, `figma-generate-design` for layouts, `figma-generate-library` for components/tokens, and `figma-design-to-code` before design-context retrieval. Use `figma-swiftui` when translating SwiftUI. Follow each skill's prerequisites. Figma writes require authorization in the task, not repeated confirmation for already-authorized work. Without tools or access, produce a local specification and report the missing access; never invent a Figma file or node. Paid Code Connect is optional and used only when requested and available.
3. After design approval, establish or update the Design System. Inspect the existing foundations and targeted native components/screens, then finalize shared `Component`, `Token`, and `Layout` names across Figma and code. Define semantic color, typography, spacing, and radius tokens instead of arbitrary per-screen values. Keep feature-specific components local; shared components belong in the Design System only when actual reuse warrants it. Hand code additions to the app role. Do not update `design-system-map.yaml` in this step.
4. After the design and Design System are approved, hand the UI data requirements to the app scope, which drafts the GraphQL specification, including required inputs, outputs, nullability, failure states, and behavioral semantics. The design role neither reads nor edits GraphQL. If contract review requires a product or UX change, return to planning/design review and obtain approval instead of silently changing the design.
5. After the GraphQL specification is confirmed, update `design-system-map.yaml` last with the approved Figma/Design System names, actual Android/iOS component and token names, and real naming or behavior exceptions. Do not put GraphQL fields in the map. Then hand off the Figma URL/node or agreed local spec, approval state, platform differences, component/token names, mapping exceptions, interaction states, data requirements, and acceptance criteria. For visual review compare actual Android/iOS renders with that reference: spacing, type/line height, wrapping, color, radius, safe areas, dark mode, text scaling, and accessibility. Report differences and evidence separately for each platform. Request missing renders from app work; do not start backend work or claim that mocks, mappings, or an unrendered design prove visual parity.
