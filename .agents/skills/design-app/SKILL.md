# Design the app

[English](SKILL.md) | [한국어](SKILL.ko.md)

Use [design rules](../../../app/design/AGENTS.md). Read English except for translation maintenance. Keep design records in `app/design/`; do not read backend implementation or edit app code or GraphQL.

Enter at the requested stage and reuse approved artifacts. Existing approved Figma designs or agreed local specifications do not need to be recreated in Make; report missing source evidence only when it is needed for the requested change.

1. Confirm the approved feature plan before designing: user value, flow, target platforms, requested screens, content, and UI data concepts. Separate draft proposals from already-approved Figma or agreed local specifications. Do not read GraphQL or backend implementation as design input. Record ambiguous product decisions as planning gaps instead of letting an existing API pre-constrain the design.
2. Produce, review, and approve the requested design in Figma Make. Treat Figma Make-produced files and artifacts as design input; do not claim automatic conversion or use unsupported Make APIs. Reuse existing foundations and approved Figma components/variants, Variables, and Auto Layout when evidenced. Preserve native navigation, sheets, pickers, and safe areas for Android/Material and iOS/HIG instead of forcing identical interactions. Include relevant loading, empty, error, retry, disabled, and offline states. Obtain review of new design decisions before continuing; reuse an existing approval when it covers the work. Before any Figma tool call, inspect available capabilities and load only the operation's available prerequisite skill: `figma-create-new-file` for new files, `figma-use` for file-context reads/writes, `figma-generate-design` for layouts, `figma-generate-library` for components/tokens, and `figma-design-to-code` before design-context retrieval. Use `figma-swiftui` when translating SwiftUI. Follow each skill's prerequisites. Figma writes require authorization in the task, not repeated confirmation for already-authorized work. Without tools or access, produce a local specification and report the missing access; never invent a Figma file, node, or Make artifact. Paid Code Connect is optional and used only when requested and available.
3. After design approval, create or reconcile the Design System from approved Make artifacts, existing approved Figma designs, or an agreed local specification. Keep the actual source and approval state explicit; a local specification does not establish that Figma nodes exist. Inspect existing foundations and targeted native components/screens, then define semantic color, typography, spacing, and radius tokens and finalize shared `Component`, `Token`, and `Layout` names where evidence supports them. Keep feature-specific components local; shared components belong in the Design System only when actual reuse warrants it. Do not invent existing native symbols for a planned implementation. Hand planned code additions to the app role.
4. Before native app development, match approved Design System tokens to verified existing Android/iOS names. Update `design-system-map.yaml` only for finalized mappings and actual naming or behavior exceptions; do not put GraphQL fields or planned native symbols in the map. Put planned native additions in the handoff, clearly labeled as planned rather than existing. The design role neither reads nor edits GraphQL.
5. Hand the approved design to the app scope for native app development with the Figma Make/design reference, approval state, Design System evidence, existing token/component mappings and exceptions, planned native additions, platform differences, interaction states, accessibility requirements, and acceptance criteria. The app scope creates the GraphQL contract after native development and hands its approved contract to backend. If contract work requires a product or UX change, return it to planning/design review and obtain approval instead of silently changing the design. For visual review compare actual Android/iOS renders with the approved reference: spacing, type/line height, wrapping, color, radius, safe areas, dark mode, text scaling, and accessibility. Report differences and evidence separately for each platform. Request missing renders from app work; do not start backend work or claim that mocks, mappings, or an unrendered design prove visual parity.
