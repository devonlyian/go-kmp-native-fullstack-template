# 앱 디자인

[English](SKILL.md) | [한국어](SKILL.ko.md)

[디자인 규칙](../../../app/design/AGENTS.ko.md)을 따른다. 번역 관리 외에는 영어를 읽는다. 디자인 기록은 `app/design/`에 두며 백엔드 구현을 읽거나 앱 코드·GraphQL을 수정하지 않는다.

요청된 단계부터 진행하고 승인된 산출물을 재사용한다. 기존에 승인된 Figma 디자인이나 합의된 로컬 명세를 다시 만들 필요는 없으며 요청된 변경에 필요한 원본 근거가 없을 때만 누락을 보고한다. 모든 디자인 작업은 [디자인 기록 양식](../../../app/design/history/_template.ko.md)을 사용해 `app/design/history/` 아래 `YYYY-MM-DD-<기능-slug>.md` / `.ko.md` 문서 쌍으로 기록하고 작업이 진행될 때마다 상태를 갱신한다.

Figma 파일 규칙: 사용자가 다르게 정하지 않으면 제품당 Figma 파일 하나를 유지하고 기능 흐름마다 페이지 하나를 추가한다. 파일 URL/key·페이지 이름·노드 id를 디자인 기록에 남긴다.

1. 디자인 전에 승인된 기능 기획에서 사용자 가치·흐름·대상 플랫폼·요청 화면·콘텐츠·UI 데이터 개념을 확인한다. 초안 제안과 이미 승인된 Figma·합의한 로컬 명세를 구분한다. GraphQL이나 백엔드 구현을 디자인 입력으로 읽지 않는다. 기존 API로 디자인을 미리 제한하지 말고 모호한 제품 결정은 기획의 빈 부분으로 기록한다.
2. 승인된 시각 방향이 없으면 방향 시드를 뽑는다. 승인된 Figma 디자인·합의된 로컬 명세·확립된 제품 시각 정체성이 방향을 이미 정했다면 이 단계는 건너뛴다. 그렇지 않으면 `python3 .agents/skills/ui-ux-pro-max/scripts/search.py "<제품과 분위기 키워드>" --design-system`을 실행해 반환된 스타일·의미 기준 색 Token·타이포그래피 조합·체크리스트를 방향 후보로 사용자 검토에 제시한다. 제안 전에 네이티브 앱 기준으로 결과를 걸러낸다. 랜딩 페이지 패턴·hover/scroll 효과·웹 전용 지침은 적용하지 않고, Google Fonts는 display 글꼴로만 쓸 수 있으며 UI는 Android/iOS 시스템 글꼴이 담당한다. 시드는 추천이지 승인된 디자인이 아니다. 승인 또는 거절된 방향을 디자인 기록에 남기고, 스크립트를 쓸 수 없으면 글로 쓴 방향 제안으로 대체한다.
3. 그리기 전에 대상 파일에 읽기 전용 호출을 해서 Figma MCP 접근을 확인한다. Figma MCP에 연결할 수 없거나 rate limit이면 작업을 중단하고 실패를 보고한다. 사용자가 명시적으로 요청하지 않으면 대체 로컬 명세를 만들거나 파일을 지어내지 않는다.
4. 나머지를 그리기 전에 Figma MCP 도구로 Figma에 시제품 화면 하나를 그려 승인받는다. 가장 대표적인 화면을 고른다. 시제품 화면 승인은 전체 흐름이 아니라 방향 문법(팔레트·서체·컴포넌트 성격·간격)의 승인이다. Figma 도구 호출 전에는 사용 가능한 기능을 확인하고 해당 작업에 필요한 선행 skill만 읽는다. 새 파일은 `figma-create-new-file`, 파일 문맥 읽기/쓰기는 `figma-use`, 레이아웃은 `figma-generate-design`, 컴포넌트/Token은 `figma-generate-library`, 디자인 문맥 조회 전에는 `figma-design-to-code`다. SwiftUI 변환에는 `figma-swiftui`를 사용한다. 각 skill의 선행 조건을 따른다. Figma 쓰기는 작업 권한이 필요하지만 이미 허용된 작업에 반복 확인을 요구하지 않는다. 유료 Code Connect는 선택 사항이며 요청되고 사용 가능할 때만 쓴다.
5. 같은 Figma 파일/페이지에 승인된 시제품 문법을 적용해 전체 디자인을 만든다. 근거가 있는 기존 Foundation과 승인된 Figma 컴포넌트/Variant·Variable·Auto Layout은 재사용한다. 상호작용을 억지로 같게 만들지 말고 Android/Material과 iOS/HIG의 네이티브 Navigation·Sheet·Picker·Safe Area를 유지한다. 관련 로딩·빈 데이터·오류·재시도·비활성·오프라인 상태를 포함한다. 새 디자인 결정은 다음 단계 전에 검토받되 기존 승인에 포함된 작업은 그 승인을 재사용한다. Figma 파일·노드·산출물을 지어내지 않는다.
6. 디자인 승인을 요청하기 전에 캔버스를 자기 점검한다. 계획한 모든 상태가 프레임으로 존재하는지, 플랫폼 프레임 크기와 Safe Area를 지켰는지, 네이티브 Navigation 방식을 유지했는지, 색·텍스트가 raw 값이 아닌 의미 기반 Variable에 연결됐는지, 디자인 기록에 실제 화면과 노드 id가 적혔는지를 확인하고 빈 곳을 먼저 고친 뒤 검토를 요청한다.
7. 디자인 확정 뒤 승인된 Figma 파일 또는 합의된 로컬 명세를 바탕으로 Design System을 생성하거나 조정한다. 실제 원본과 승인 상태를 명시하며 로컬 명세만으로 Figma 노드가 존재한다고 간주하지 않는다. 기존 Foundation과 대상 네이티브 컴포넌트·화면을 살펴본 뒤, 근거가 있을 때 의미 기반 색·타이포그래피·간격·반경 Token을 정의하고 Figma와 코드의 공용 `Component`, `Token`, `Layout` 이름을 확정한다. 기능 전용 컴포넌트는 기능 안에 두며 실제 재사용이 필요한 공용 컴포넌트만 Design System에 둔다. 계획된 구현에 기존 네이티브 심볼을 지어내지 않는다. 계획된 코드 추가는 앱 역할에 인계한다.
8. 네이티브 앱 개발 전에 승인된 Design System Token을 검증된 기존 Android/iOS 이름에 매칭한다. 확정된 매핑과 실제 이름·동작 예외만 `design-system-map.yaml`에 갱신하며, GraphQL 필드와 계획 중인 네이티브 심볼은 맵에 넣지 않는다. 계획된 네이티브 추가 항목은 인계에 기존 항목과 구분해 명시한다. 디자인 역할은 GraphQL을 읽거나 수정하지 않는다.
9. 디자인 기록 경로, Figma 파일/디자인 참조, 승인 상태, Design System 근거, 기존 Token·컴포넌트 매핑과 예외, 계획된 네이티브 추가 항목, 플랫폼 차이, 상호작용 상태, 접근성 요구사항, 완료 조건을 포함해 승인된 디자인을 네이티브 앱 개발을 담당하는 app 범위에 인계한다. app 범위는 네이티브 개발 뒤 GraphQL 계약을 만들고 승인된 계약을 백엔드에 인계한다. 계약 작업에 제품·UX 변경이 필요하면 디자인을 조용히 바꾸지 말고 기획·디자인 검토로 돌아가 승인을 받는다. 시각 검토에서는 실제 Android/iOS 렌더링을 승인된 기준과 비교한다. 간격·글꼴/행간·줄바꿈·색·반경·Safe Area·다크 모드·글자 확대·접근성을 확인한다. 차이와 증거는 플랫폼별로 보고한다. 없는 렌더링은 앱 작업에 요청하고 백엔드 작업을 시작하지 않는다. Mock·매핑·렌더링하지 않은 디자인이 시각적 일치의 증거라고 주장하지 않는다.
