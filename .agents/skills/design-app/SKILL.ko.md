# 앱 디자인

[English](SKILL.md) | [한국어](SKILL.ko.md)

[디자인 규칙](../../../app/design/AGENTS.ko.md)을 따른다. 번역 관리 외에는 영어를 읽는다. 디자인 기록은 `app/design/`에 두며 백엔드 구현을 읽거나 앱 코드·GraphQL을 수정하지 않는다.

요청된 단계부터 진행하고 승인된 산출물을 재사용한다. 기존에 승인된 Figma 디자인이나 합의된 로컬 명세를 Make에서 다시 만들 필요는 없으며 요청된 변경에 필요한 원본 근거가 없을 때만 누락을 보고한다.

1. 디자인 전에 승인된 기능 기획에서 사용자 가치·흐름·대상 플랫폼·요청 화면·콘텐츠·UI 데이터 개념을 확인한다. 초안 제안과 이미 승인된 Figma·합의한 로컬 명세를 구분한다. GraphQL이나 백엔드 구현을 디자인 입력으로 읽지 않는다. 기존 API로 디자인을 미리 제한하지 말고 모호한 제품 결정은 기획의 빈 부분으로 기록한다.
2. 요청된 디자인을 Figma Make에서 만들고 검토·확정한다. Figma Make가 만든 파일과 산출물을 디자인 입력으로 다루며, 자동 변환을 주장하거나 지원되지 않는 Make API를 사용하지 않는다. 근거가 있는 기존 Foundation과 승인된 Figma 컴포넌트/Variant·Variable·Auto Layout은 재사용한다. 상호작용을 억지로 같게 만들지 말고 Android/Material과 iOS/HIG의 네이티브 Navigation·Sheet·Picker·Safe Area를 유지한다. 관련 로딩·빈 데이터·오류·재시도·비활성·오프라인 상태를 포함한다. 새 디자인 결정은 다음 단계 전에 검토받되 기존 승인에 포함된 작업은 그 승인을 재사용한다. Figma 도구 호출 전에는 사용 가능한 기능을 확인하고 해당 작업에 필요한 선행 skill만 읽는다. 새 파일은 `figma-create-new-file`, 파일 문맥 읽기/쓰기는 `figma-use`, 레이아웃은 `figma-generate-design`, 컴포넌트/Token은 `figma-generate-library`, 디자인 문맥 조회 전에는 `figma-design-to-code`다. SwiftUI 변환에는 `figma-swiftui`를 사용한다. 각 skill의 선행 조건을 따른다. Figma 쓰기는 작업 권한이 필요하지만 이미 허용된 작업에 반복 확인을 요구하지 않는다. 도구나 접근 권한이 없으면 로컬 명세를 만들고 누락된 접근을 알리며 Figma 파일·노드·Make 산출물을 지어내지 않는다. 유료 Code Connect는 선택 사항이며 요청되고 사용 가능할 때만 쓴다.
3. 디자인 확정 뒤 승인된 Make 산출물·기존 승인 Figma 디자인·합의된 로컬 명세를 바탕으로 Design System을 생성하거나 조정한다. 실제 원본과 승인 상태를 명시하며 로컬 명세만으로 Figma 노드가 존재한다고 간주하지 않는다. 기존 Foundation과 대상 네이티브 컴포넌트·화면을 살펴본 뒤, 근거가 있을 때 의미 기반 색·타이포그래피·간격·반경 Token을 정의하고 Figma와 코드의 공용 `Component`, `Token`, `Layout` 이름을 확정한다. 기능 전용 컴포넌트는 기능 안에 두며 실제 재사용이 필요한 공용 컴포넌트만 Design System에 둔다. 계획된 구현에 기존 네이티브 심볼을 지어내지 않는다. 계획된 코드 추가는 앱 역할에 인계한다.
4. 네이티브 앱 개발 전에 승인된 Design System Token을 검증된 기존 Android/iOS 이름에 매칭한다. 확정된 매핑과 실제 이름·동작 예외만 `design-system-map.yaml`에 갱신하며, GraphQL 필드와 계획 중인 네이티브 심볼은 맵에 넣지 않는다. 계획된 네이티브 추가 항목은 인계에 기존 항목과 구분해 명시한다. 디자인 역할은 GraphQL을 읽거나 수정하지 않는다.
5. Figma Make/디자인 참조, 승인 상태, Design System 근거, 기존 Token·컴포넌트 매핑과 예외, 계획된 네이티브 추가 항목, 플랫폼 차이, 상호작용 상태, 접근성 요구사항, 완료 조건을 포함해 승인된 디자인을 네이티브 앱 개발을 담당하는 app 범위에 인계한다. app 범위는 네이티브 개발 뒤 GraphQL 계약을 만들고 승인된 계약을 백엔드에 인계한다. 계약 작업에 제품·UX 변경이 필요하면 디자인을 조용히 바꾸지 말고 기획·디자인 검토로 돌아가 승인을 받는다. 시각 검토에서는 실제 Android/iOS 렌더링을 승인된 기준과 비교한다. 간격·글꼴/행간·줄바꿈·색·반경·Safe Area·다크 모드·글자 확대·접근성을 확인한다. 차이와 증거는 플랫폼별로 보고한다. 없는 렌더링은 앱 작업에 요청하고 백엔드 작업을 시작하지 않는다. Mock·매핑·렌더링하지 않은 디자인이 시각적 일치의 증거라고 주장하지 않는다.
